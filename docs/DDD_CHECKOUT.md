# Домен оформления заказа

Изменения ограничены заказами — здесь есть денежные расчёты, конкурентные записи,
история покупки и жизненный цикл. Баннеры и справочники остаются CRUD-модулями.
Проект не объявляется полностью переработанным в DDD или готовым банковским ядром.

## Границы и зависимости

| Слой | Ответственность | Зависимости |
|---|---|---|
| `order/domain` | Money, позиции и суммы заказа, ограничения количества/остатков, переходы статуса | Только TypeScript |
| `order/application` | PlaceOrder, ChangeOrderStatus, интерфейсы транзакционного хранения | Только домен |
| `order/infrastructure` | Sequelize-транзакции, блокировки, запись снимков, проекция для API | Реализует интерфейсы application |
| `place-order.service.ts`, `order.queries.ts` | Адаптация старого RMQ-контракта, композиция Nest | Вызывает прикладные сценарии |
| `order.repository.ts` | Чтение для экранов и списков | ORM и проекция; команд записи больше нет |

Агрегат `CheckoutOrder` владеет позициями и итогами покупки. Пользователь и каталог
не становятся его частями: входом служат идентификаторы и снимки каталога.
Проверка доступности — политика оформления по заблокированным данным. Списание
остатков выполняет адаптер в общей локальной транзакции, потому что сейчас каталог
и заказы находятся в одной БД. Разделение на разные БД потребует протокола резервирования.

`PlaceOrder` получает `CheckoutUnitOfWork`. Внутри сессии он читает корзину, каталог,
создаёт допустимый заказ, сохраняет его и удаляет только использованные строки
корзины. Тип Sequelize Transaction не выходит за пределы адаптера.
Обработчики не передают ORM-модели в домен и не возвращают их из сценария создания.

## Бизнес-гарантии

- Money хранит целые копейки RUB; дробные копейки не округляются молча.
  Переполнение и потеря копейки при преобразовании в старый числовой контракт запрещены.
- Позиции одного товара из разных строк корзины объединяются до проверки остатков.
- Цена и название фиксируются в OrderFood в момент оформления. Обновление каталога
  не меняет отображаемые позиции новых заказов.
- Immutable-модель нельзя изменить через ссылку на входной массив или объект.
- В PostgreSQL сначала блокируются строки корзины, затем товары по возрастанию ID.
  Создание заказа, списание и очистка корзины фиксируются или откатываются вместе.
- `ChangeOrderStatus` блокирует строку заказа и принимает только id/status.
  Пользовательский payload не может изменить owner, суммы, isPaid или completed.
- Для доставки: created → confirmed → delivery → received.
  Для самовывоза: created → confirmed → received. Повтор текущего статуса идемпотентен.
  Обратные переходы и пропуск этапов запрещены; completed выводится из received.
- API возвращает allowedStatuses из домена; frontend отключает недоступные варианты.

Это явно выбранный протокол на основе существующих четырёх статусов интерфейса.
Отмена, возврат, повторная доставка и подтверждение оплаты не придумываются здесь:
для них нужны отдельные команды и согласованные бизнес-правила.

## Совместимость и миграция

Перед запуском новой версии account на существующей БД выполни
`delivery-service/migrations/002-order-line-snapshots.sql`.
Миграция добавляет nullable `productTitle` и `unitPriceMinor` в `OrderFoods`,
не удаляет данные и допускает повторное выполнение.

Историческую цену невозможно восстановить из текущего каталога. Старые строки
остаются с NULL-снимками; совместимая проекция использует каталог только для таких
строк. Поэтому гарантия исторической цены относится к заказам, созданным новой версией.
Перевод всех старых сумм с DOUBLE на точные SQL-типы остаётся отдельной миграцией.

Для локального Kubernetes можно передать SQL в PostgreSQL Pod, используя credentials
самого контейнера, не выводя их в терминал (из корня репозитория):

```powershell
Get-Content delivery-service/migrations/002-order-line-snapshots.sql -Raw | kubectl --context kind-flowing-delivery -n flowing-delivery-lab exec -i postgres-0 -- sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d delivery'
```

Затем собирается новый образ, загружается в kind и обновляется Deployment account.
Текущая работа проверена отдельным образом `flowing-delivery-backend:ddd`;
запущенная лаборатория автоматически не переключается на эту ветку.

Контракт `order.update.command` теперь предназначен только для статуса.
Редактирование цены, способа получения и адреса через общий update не поддерживается.
Публичные поля ответа создания заказа сохранены, суммы блюд/итога и флаги из
старого запроса создания не входят в прикладную команду.

## Проверки

Локально прошли 29 domain/application тестов, 27 PostgreSQL integration тестов
(включая сагу) и 3 теста API заказа. Linux backend-образ и frontend TypeScript/Vite
собраны успешно. Применение к работающей БД и rollout этой ветки не выполнялись.

```powershell
cd delivery-service
npm.cmd run test:domain
# Для локальной одноразовой PostgreSQL из docker-compose.transactions.yml:
$env:TRANSACTION_TEST_DATABASE_URL='postgres://transaction_student:local-test-only@127.0.0.1:55432/delivery_transactions_test'
npm.cmd run test:transactions
```

Domain/application тесты не поднимают Nest или БД. Проверка зависимостей запрещает
им импортировать Nest, Sequelize, transport contracts и ORM-модели.
Интеграционные тесты проверяют реальные блокировки/откат, изменения каталога,
повторную миграцию без ложного backfill и конкурентные команды статуса.
CI запускает оба набора.

## Что остаётся за границей

Тариф доставки всё ещё приходит из старого контракта — нужна серверная котировка.
Авторизация операций и преобразование транспортных ошибок также требуют отдельной
доработки; доменные ограничения не заменяют контроль доступа. Сага остаётся отдельным
стендом, уведомления не получили transactional outbox. Запуск account всё ещё содержит
legacy synchronize/seed. Эти ограничения не скрываются новой структурой каталогов.
