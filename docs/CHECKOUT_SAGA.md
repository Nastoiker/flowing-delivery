# Checkout saga v1

Оркестратор: `delivery-service/apps/account/src/app/order/saga/checkout-saga.ts`.
Он пока **не подключён к HTTP/RMQ оформлению заказа**: действующий `PlaceOrderService`
сохраняет локальную транзакцию заказа и остатков. Платёжный провайдер не вызывается.
Тестовые участники моделируют эффекты в PostgreSQL; это не реализация эквайринга.

## Протокол

Последовательность: резерв остатков → платёж → подтверждение исполнения.
Если платёж отклонён, освобождается резерв. Если исполнение отклонено после оплаты,
выполняются возврат платежа и освобождение резерва, строго в этом порядке.
Неизвестный результат (таймаут, потеря ответа) оставляет шаг незавершённым.
Повтор использует тот же ключ; таймаут не означает отказ платежа.

`start(id, input)` фиксирует намерение; `resume(id)` выполняет шаги;
`recover(limit)` подбирает незавершённые экземпляры после перезапуска.
Деньги передаются целыми копейками с явной валютой RUB. Один `orderId` допускает
одну сагу, даже если клиент меняет ключ запроса. Повтор ключа с другой суммой запрещён.

Состояние и аудит перехода сохраняются одной PostgreSQL-транзакцией.
Версия строки защищает от конкурирующих переходов. Сетевые вызовы выполняются
за пределами транзакции. После сбоя между эффектом участника и сохранением перехода
вызов повторится: гарантия — **at-least-once**, а не exactly-once.

Каждый production-адаптер обязан атомарно сохранять бизнес-эффект, ключ и результат
в собственной БД. Повтор должен вернуть прежний результат даже после компенсации.
Для внешнего платежа это требует поддержки idempotency/status reconciliation
провайдером: одна локальная таблица не закрывает окно сбоя внешнего API.
`rejected` разрешён только при достоверном отсутствии эффекта.
Ошибки транспорта должны бросать исключение. Компенсация тоже идемпотентна.

## Запуск проверок

Из корня репозитория:

```powershell
docker compose -f docker-compose.transactions.yml up -d --wait
$env:TRANSACTION_TEST_DATABASE_URL='postgres://transaction_student:local-test-only@127.0.0.1:55432/delivery_transactions_test'
cd delivery-service
npm.cmd ci
npm.cmd run test:transactions
```

Тесты разрешены только для локальной `delivery_transactions_test`.
Тесты заказа пересоздают ORM-таблицы; тесты саги очищают свои таблицы в схеме
`checkout_saga_test`. Рабочую БД указывать нельзя.

Проверяются конкурентные старты/воркеры, изменённый payload, второй ключ одного
заказа, некорректные денежные значения, отказ резерва/оплаты, потеря ответа после
платежа, потеря ответа после возврата и возобновление новым экземпляром оркестратора.

## Граница следующей интеграции

SQL-миграция `delivery-service/migrations/001-checkout-saga.sql` применяется явно.
Схему workflow v1 и порядок шагов нельзя менять для уже начатых экземпляров.
`recover()` нужно вызывать из worker с ограниченными таймаутами адаптеров,
backoff, метриками возраста незавершённых саг и сигнализацией ручного разбора.
Сейчас планировщик, backoff и production-адаптеры не реализованы.

Подключать резервирование поверх существующего списания в `PlaceOrderService`
нельзя: это удвоит списание. Сначала нужны состояния резерва, атомарный inbox
участников и согласованный переход заказа. При переходе на брокер команды должны
сохраняться в transactional outbox, а публикация — подтверждаться брокером.

Основание решения: [Saga](https://microservices.io/patterns/data/saga.html),
[Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html).
