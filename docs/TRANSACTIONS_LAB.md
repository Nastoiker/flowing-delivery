# Практикум: транзакции и конкурентное оформление заказа

Работаем с реальным сценарием проекта. Цель — уметь объяснить и доказать атомарность, изоляцию, блокировки и границу между результатом заказа и доставкой уведомления.

Этот этап не превращает проект в готовый коммерческий сервис: доступ к административным операциям, идемпотентность, outbox и тариф доставки требуют следующих изменений. Исходное ревью относится к старому состоянию; текущие локальные исправления перечислены здесь.

## Что изменено

1. [PlaceOrderService](../delivery-service/apps/account/src/app/order/place-order.service.ts) владеет транзакцией оформления.
2. [OrderQueries](../delivery-service/apps/account/src/app/order/order.queries.ts) только принимает RMQ-команду и вызывает сценарий.
3. [OrderRepository](../delivery-service/apps/account/src/app/order/order.repository.ts) принимает обязательный transaction при записи заказа, позиций, сумм и списании.
4. [ShoppingCartRepository](../delivery-service/apps/account/src/app/shopping-cart/repositories/Shopping-cart.repositories.ts) блокирует оформляемые строки и удаляет только их ID.
5. [OrderController](../delivery-service/apps/api/src/app/controllers/order.controller.ts) сохраняет результат успешного заказа при ошибке уведомления и не даёт body перекрыть userId из авторизации.
6. Сумма блюд считается по ценам заблокированных товаров. Статус нового заказа всегда created; поля isPaid/completed не принимаются из тела.
7. В коде есть русские комментарии о причинах решений. Схема БД не изменялась.

## Реализованные гарантии и ограничения

| Свойство | Сейчас |
|---|---|
| Заказ, позиции, списания, суммы и удаление оформленных позиций | Одна локальная транзакция PostgreSQL |
| Ошибка после любого из этих шагов | Откат всей транзакции |
| Два оформления существующих строк одной корзины | Строковые блокировки; второй не оформляет те же строки повторно |
| Два покупателя последнего товара | Блокировка товара; один успех, второй видит новый остаток |
| Новая позиция корзины во время оформления | Не удаляется, если не попала в выбранные ID |
| Сумма блюд | Рассчитывается на сервере; клиентские priceFood/totalPrice игнорируются |
| Тариф доставки | Пока доверяется прежнему контракту после проверки числа; подмена тарифа ещё возможна |
| Историческая цена каждой позиции | Пока не сохраняется; нужен отдельный этап с миграцией |
| Повтор запроса после потери ответа | Нет полной идемпотентности; пустая корзина может дать отказ |
| Уведомление | Ошибка не отменяет заказ, но доставка не гарантирована и ожидание RMQ может задержать ответ |
| Падение процесса после COMMIT | Заказ сохранён; уведомление может потеряться до внедрения outbox |
| Другие операции с остатками и корзиной | Не переработаны полностью; старые широкие update могут нарушить правила |
| Ошибки API | Старое преобразование многих ошибок в 401 остаётся отдельной задачей |

## Как запустить проверки

Нужны Node.js, зависимости delivery-service и работающий Docker Desktop с Linux containers. Используется отдельный Compose-проект и одноразовая БД на порту 55432. Рабочие env и volumes не используются.

Из корня репозитория:

```powershell
docker compose -f docker-compose.transactions.yml up -d --wait
Set-Location delivery-service
npm ci
$env:TRANSACTION_TEST_DATABASE_URL = 'postgres://transaction_student:local-test-only@127.0.0.1:55432/delivery_transactions_test'
npm run test:transactions
npx jest --config apps/api/jest.config.ts --runInBand --runTestsByPath apps/api/src/app/controllers/order.controller.spec.ts
```

Учебный пароль относится только к локальной одноразовой БД. Тесты удаляют и пересоздают её таблицы. Есть защита: допускаются только localhost/127.0.0.1 и имя delivery_transactions_test. Не используй эту БД для своих данных.

Без URL специальная команда завершится ошибкой. При обычном запуске Jest без URL интеграционный набор пропускается: это не доказательство работоспособности транзакций.

После занятия из корня:

```powershell
docker compose -f docker-compose.transactions.yml down
Remove-Item Env:TRANSACTION_TEST_DATABASE_URL -ErrorAction SilentlyContinue
```

Данные тестового PostgreSQL хранятся в tmpfs и удаляются вместе с контейнером.

## Занятие 1. Атомарность: 40–60 минут

**Прочитай:** PlaceOrderService.execute и тест «откатывает первое списание…».

Транзакция охватывает:
```text
BEGIN
  SELECT позиции корзины FOR UPDATE
  INSERT заказ
  Для товаров по возрастанию productId:
    SELECT товар FOR UPDATE
    Проверка количества, остатка, цены
    UPDATE остатки
    INSERT позиция заказа
  UPDATE суммы заказа
  DELETE выбранные позиции корзины
COMMIT
```

Sequelize управляет завершением: исключение из callback вызывает ROLLBACK, успешный callback — COMMIT. execute разрешает Promise после завершения транзакции.

**Предскажи:** если второго товара нет, останется ли заказ? Изменится ли первый товар? Вернётся ли корзина?

**Проверь:** тест сравнивает все затронутые таблицы. Второй тест внедряет исключение после настоящего DELETE корзины — даже удаление откатывается.

**Учебный эксперимент:** временно убери передачу transaction только из createOrder и запусти тест отката. Ожидается оставшийся заказ и падение проверки. Затем восстанови transaction. Такой эксперимент выполняй только на одноразовой БД.

**Объясни своими словами:** почему try/catch сам по себе не откатывает SQL; почему нельзя поймать ошибку внутри transaction callback и вернуть обычный результат; почему всем запросам нужно передать один transaction.

Не ожидай непрерывных ID: значения PostgreSQL sequence обычно не возвращаются при ROLLBACK. Пропуски номеров сами по себе не доказывают потерю заказа.

## Занятие 2. Конкурентный доступ: 60–90 минут

**Прочитай:** createFoodForOrder и последний интеграционный тест.

Без блокировки возможна ситуация:
```text
A читает остаток 1
B читает остаток 1
A записывает 0 и создаёт позицию
B записывает 0 и создаёт позицию
Итого: две продажи, хотя остаток не стал отрицательным
```

Нулевой остаток не доказывает отсутствие перепродажи!

FOR UPDATE удерживает строку до COMMIT/ROLLBACK. При READ COMMITTED ожидающий запрос после разблокирования получает актуальную версию строки и повторно проверяет остаток.

Тест сначала блокирует товар третьим соединением. Затем запускает два оформления и через pg_stat_activity подтверждает, что оба ждут блокировку. Только после этого освобождает товар. Поэтому проверяется реальное пересечение запросов.

**Практика:** временно убери блокировку товара и запусти последний тест. Проверка наблюдаемых ожидающих запросов или конечного результата должна выявить нарушение. Верни блокировку.

**Объясни:** почему обычный SELECT не обязательно блокируется; чем атомарность отличается от изоляции; почему обработка запросов в одном Node.js процессе не делает операции с БД последовательными.

## Занятие 3. Порядок блокировок и граница корзины: 45 минут

Две корзины могут содержать товары в разном порядке. Захват A → B одним запросом и B → A другим создаёт возможность deadlock. Поэтому товары сортируются по productId.

Это уменьшает риск для данного сценария, но не гарантирует отсутствия всех deadlock: другие операции тоже должны соблюдать согласованный порядок.

Корзина читается отдельным запросом без JOIN. Это делает область блокировки понятной и не затрагивает наружные соединения с пользователем/товарами.

Удаление ограничено ID прочитанных позиций. Широкий DELETE WHERE userId может удалить новую позицию, добавленную после чтения корзины. Отдельный тест проверяет именно это.

**Задание:** добавь тест с двумя корзинами, в которые товары добавлены в обратном порядке; задай достаточно остатков для обоих заказов и проверь два успеха.

**Вопрос повышенной сложности:** что произойдёт, если параллельно изменить количество уже заблокированной позиции? Найди, что делает текущий updateShoppingCart после ожидания и удаления строки. Предложи явный конфликт вместо мнимого успешного обновления.

## Занятие 4. Бизнес-правила внутри транзакции: 45 минут

В коде проверяются положительное целое количество, корректность остатков и цены. Суммы позиций считаются в копейках, затем записываются в существующие поля рублей. Это промежуточное решение: типы БД DOUBLE пока не мигрированы.

Во время запуска Sequelize предупреждает, что PostgreSQL не поддерживает UNSIGNED. Это полезный сигнал: INTEGER.UNSIGNED в модели не создаёт запрет отрицательных значений в этой БД.

**Задание:** спроектируй миграцию CHECK для количества/остатков, сначала определив правила для существующих данных. Запрет отрицательной величины не решает конкурентную перепродажу — нужна также корректная операция списания.

**Следующий PR:** серверный тариф доставки и снимок цены/названия позиции. Не добавляй тариф «200 рублей» без бизнес-основания.

## Занятие 5. Успех заказа и доставка сообщения: 45–60 минут

После ответа account транзакция уже завершена. Ошибка поиска администраторов или WebSocket не должна превращать этот результат в отказ.

API-тесты проверяют:
- ошибка получения администраторов не портит результат;
- исключение при отправке WebSocket не портит результат;
- при ошибке создания уведомление об успехе не отправляется;
- userId из тела не перекрывает идентификатор авторизации.

Это ещё не гарантированная доставка. Процесс может упасть между COMMIT и уведомлением, а ожидание брокера может задержать HTTP-ответ.

**Спроектируй следующий этап:** таблица outbox, запись события в той же транзакции, отдельный издатель, уникальный eventId и обработка дублей получателем. Объясни, что случится, если брокер примет сообщение, но издатель упадёт до отметки об отправке.

Не делай сетевой вызов платёжному провайдеру внутри длительной транзакции остатков.

## Занятие 6. Идемпотентность: отдельная гарантия

Два одновременных оформления одних строк корзины сейчас не создают два заказа. Но это не полная идемпотентность.

Пример: COMMIT прошёл, HTTP-ответ потерян. Повтор видит пустую корзину и возвращает ошибку. Пользователь не получает исходный orderId.

**Задание:** предложи хранение ключа с областью userId + операция, отпечатком запроса и resultOrderId. Определи:
1. Что вернуть при повторе того же содержимого?
2. Что вернуть при том же ключе и другом содержимом?
3. Как два одновременных запроса с одним ключом защищаются ограничением уникальности?
4. Как сохранить ключ и результат вместе с заказом?
5. Как обрабатывать таймаут, если неизвестно, завершился ли COMMIT?

До реализации этих правил нельзя обещать «ровно один заказ для каждого повторяемого запроса».

## Результаты проверки этого изменения

На отдельном PostgreSQL 16: 10 интеграционных сценариев. На API: 3 теста контроллера. Сборки account/api проверяются отдельно от тестов. Тесты запускают прикладной сервис с реальными Sequelize-моделями и репозиториями; это не полный HTTP → RabbitMQ → PostgreSQL тест.

Рабочая БД, миграции действующего окружения и полноценная доставка уведомлений этими проверками не покрыты.
