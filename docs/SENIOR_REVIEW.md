# Senior review: flowing-delivery

Ревью исходного состояния `ed26e91`. Цель — научиться обеспечивать бизнес-гарантии и диагностировать распределённую систему. Оценка архитектуры не равна оценке автора или диплома. Нагрузочные проверки и эксплуатация не проводились.

## Задумка и удачные решения

React-клиент общается с Nest API; API вызывает обработчики через RabbitMQ. Account содержит пользователей, каталог, корзину и заказы. Баннеры, платежи и события выделены в отдельные приложения. Контракты вынесены в общую библиотеку. Есть внедрение зависимостей, репозитории, bcrypt и Docker.

Это хороший учебный охват. Отдельный процесс полезен, когда есть самостоятельная ответственность, жизненный цикл или потребность масштабирования. Монорепозиторий и один сервер PostgreSQL сами по себе не ошибки. Основной вопрос — какие гарантии сохраняются при сбое и кто владеет данными.

## Приоритеты

P0 — закрыть до внешнего доступа. P1 — корректность основного сценария. P2 — сопровождаемость и эксплуатация. Это приоритеты данного проекта, а не формальная оценка CVSS.

### R1 / P0: входные DTO позволяют менять защищённые поля

**Где:** [user.controller.ts](../delivery-service/apps/api/src/app/controllers/user.controller.ts), [user.repositories.ts](../delivery-service/apps/account/src/app/user/repositories/user.repositories.ts).

`Partial<IUser>` содержит идентификатор, роль, пароль и статус. В `{ id: userId, ...updateDto }` клиентский ID может перекрыть доверенный. Репозиторий сохраняет остаток объекта без списка разрешённых полей.

**Развитие:** отделить входную команду от ORM-модели, задавать actorId из авторизации; операции смены роли и пароля сделать отдельными. Перестановка spread решает только часть проблемы.

**Готово, когда:** пользователь A не меняет B; редактирование профиля не меняет роль/статус/пароль; API-тест проверяет прямой запрос без UI.

### R2 / P0: права на объект не следуют из наличия JWT

**Где:** [shopping-cart.controller.ts](../delivery-service/apps/api/src/app/controllers/shopping-cart.controller.ts), [Shopping-cart.repositories.ts](../delivery-service/apps/account/src/app/shopping-cart/repositories/Shopping-cart.repositories.ts), [order.controller.ts](../delivery-service/apps/api/src/app/controllers/order.controller.ts).

Обновление корзины получает userId, но не использует его; удаление передаёт только ID. Поиск записи не ограничен владельцем. Обновление заказа не защищено guard; JWT на других операциях не проверяет административную роль.

**Развитие:** проверять субъект, объект и разрешённое действие. Предикат владения должен участвовать в чтении/изменении записи. Для администратора — явная политика.

**Готово, когда:** матрица guest / user A / user B / admin проверена для read/update/delete. Неавторизованный запрос не изменяет данные.

### R3 / P0: публичный ответ использует внутреннюю модель пользователя

**Где:** [UserRepository.me](../delivery-service/apps/account/src/app/user/repositories/user.repositories.ts), [user.queries.ts](../delivery-service/apps/account/src/app/user/queries/user.queries.ts).

`findByPk` возвращает модель с password, затем она передаётся как profile. Вложенные User при чтении заказов/корзины тоже требуют проверки. Это вывод по цепочке кода; HTTP-ответ в данном ревью не воспроизводился.

**Развитие:** явный публичный DTO и маппинг разрешённых полей, включая вложенные объекты.

**Готово, когда:** ответы и логи не содержат password/hash/token; тест проверяет вложенные структуры.

### R4 / P1: оформление заказа не атомарно и допускает гонки

**Где:** [order.queries.ts](../delivery-service/apps/account/src/app/order/order.queries.ts), [order.repository.ts](../delivery-service/apps/account/src/app/order/order.repository.ts).

Заказ создаётся раньше списаний; товары обрабатываются последовательно; корзина очищается отдельно. При ошибке изменения частично сохраняются. Два запроса могут прочитать одинаковый остаток.

**Развитие:** транзакция для всех записей плюс блокировки строк или условное атомарное списание. Одна транзакция без защиты read-modify-write не доказывает отсутствие гонки. Для этих данных пока достаточно одной БД; saga не нужна.

**Готово, когда:** ошибка на втором товаре откатывает всё; два конкурентных заказа последней единицы дают ровно один успех; отрицательное/дробное количество отклоняется. Проверять с настоящим PostgreSQL, не только с mock.

### R5 / P1: клиент задаёт сумму и статус заказа

**Где:** [OrderCreateDto](../delivery-service/apps/api/src/app/dtos/order/OrderCreateDto.ts), [order-food.model.ts](../delivery-service/apps/account/src/app/order/order-food.model.ts), [order.model.ts](../delivery-service/apps/account/src/app/order/order.model.ts).

Сумма и статус приходят с клиента; в рассмотренном сценарии сервер их не пересчитывает. Позиция заказа не хранит историческую цену. Денежные поля используют floating point.

**Развитие:** серверный расчёт, деньги в минимальных целых единицах или точном decimal, снимок названия/цены позиции, разрешённые переходы состояния. Идентификатор пользователя не брать из body.

**Готово, когда:** изменение меню не меняет историю заказа; подмена цены не влияет на итог; невозможен произвольный переход delivered → created.

### R6 / P1: частичный успех и повтор запроса не определены

**Где:** [order.controller.ts](../delivery-service/apps/api/src/app/controllers/order.controller.ts).

После создания заказа API запрашивает администраторов. Ошибка второго запроса превращает уже успешное оформление в ошибку для клиента. В сценарии создания не найден ключ идемпотентности.

**Развитие:** определить границу результата, вынести уведомления, фиксировать idempotency key и результат одной транзакцией; при гарантированной доставке — outbox. RabbitMQ может повторно доставлять сообщения.

**Готово, когда:** потеря ответа и повтор дают тот же orderId; отказ уведомлений не ломает заказ; восстановление доставки не дублирует бизнес-изменения.

### R7 / P0 для реальных платежей: интеграция остаётся демонстрационной

**Где:** [payment.controller.ts](../delivery-service/apps/api/src/app/controllers/payment.controller.ts), [payment.queries.ts](../delivery-service/apps/payment/src/app/payment.queries.ts), [PaymentForm](../frontend/src/features/payment/PaymentForm.tsx).

sender фиксирован, operation_id случайный, проверка подписи в обработчике не найдена; форма содержит конкретного получателя и буквальный label. Kubernetes не делает это безопасной оплатой.

**Развитие:** использовать sandbox провайдера, проверять подпись, сумму, валюту и связь с заказом; принимать дубли идемпотентно; ожидать запись в БД перед подтверждением обработки.

**Готово, когда:** неверная подпись отклоняется, дубль не меняет результат, подтверждается именно нужный заказ. В лаборатории оплату не выполнять.

### R8 / P2: границы сервисов и транспорт не обоснованы

Account содержит почти весь бизнес, banner выделен отдельно. Большая часть взаимодействий — RPC с ожиданием ответа через брокер. Брокер добавляет зависимость, но не отменяет ожидание доступности сервиса.

**Развитие:** для каждого сервиса описать владельца данных, контракт, ожидаемую нагрузку и поведение при отказе. Допустимо оставить account модульным ядром. Число процессов не является показателем зрелости.

**Готово, когда:** можно объяснить, зачем каждый сервис отделён и какие изменения он позволяет выпускать независимо.

### R9 / P2: горизонтальное масштабирование пока некорректно

**Где:** [socket.gateway.ts](../delivery-service/apps/api/src/app/socket.gateway.ts), [file.service.ts](../delivery-service/apps/api/src/app/file.service.ts).

Map сокетов локален процессу и хранит одно подключение на пользователя. Загрузка пишет на диск API. Две реплики не разделяют эти состояния.

**Развитие:** rooms и несколько соединений пользователя; межпроцессная доставка Socket.IO; общее объектное хранилище. До этого — одна реплика API. PVC лаборатории сохраняет файлы, но не решает распределённые сокеты.

**Готово, когда:** уведомление приходит при запросе к другой реплике и при нескольких вкладках; файл доступен после пересоздания Pod.

### R10 / P2: диагностика, миграции и тесты

Повторяется requestId='adad'; почти любые ошибки превращаются в 401. Включён synchronize; тесты преимущественно шаблонные Hello API. В Git уже отслеживаются env-файлы — .gitignore не удаляет их из истории.

**Развитие:** уникальный correlation ID, различение 401/403/404/409/5xx, миграции, интеграционные сценарии. Проверить отслеживаемые конфигурации и заменить реальные секреты, если они использовались; значения в ревью не публиковать.

**Готово, когда:** один заказ прослеживается по логам; ошибка остатков не выглядит как неверный пароль; база разворачивается воспроизводимо; секреты не попадают в новые образы.

### R11 / P2: клиентские состояния

**Где:** [ProtectedRoute](../frontend/src/helpers/ProtectedRoute.tsx), [SideBarShoppingCard](../frontend/src/features/shopping-card/Sidebar/SideBarShoppingCard.tsx).

Toast вызывается в render; ошибка загрузки корзины отдельно не показана; есть два API-клиента с фиксированным localhost.

**Развитие:** разделить loading/error/empty/success, побочные эффекты вынести из render, централизовать конфигурацию API.

**Готово, когда:** сетевой сбой не выглядит как пустая корзина; повторный render не порождает повторные уведомления.

## Порядок учебных PR

1. Права, DTO, публичные ответы. Доказательство: тесты двух пользователей.
2. Атомарное оформление и историческая стоимость. Доказательство: откат и конкурентный заказ.
3. Идемпотентность и переходы статусов. Доказательство: потеря ответа/повтор.
4. Outbox и диагностика. Доказательство: сбой доставки и восстановление.
5. Масштабирование после устранения локального состояния.

Не переписывать всё на новый стек. Один завершённый сценарий с гарантиями полезнее ещё нескольких сервисов.

## Оценка постановки задачи

**7/10 для развития.** Хорошо: реальный код, запрос на объяснение замысла, reviewable PR и конкретный инструмент для освоения. Не хватает среды запуска, границ изменений, ожидаемого уровня Kubernetes и проверяемого результата. Ревью архитектуры и освоение эксплуатации — две цели, их стоит принимать отдельно.

Уточнённая формулировка:

> В ветке senior подготовь ревью исходного commit с приоритетами, ссылками и критериями исправления. Добавь локальную Kubernetes-лабораторию для Docker Desktop на Windows: сборка образов, конфигурация, Secret, storage, диагностика и упражнения. Не исправляй все бизнес-дефекты автоматически; исправь только блокеры запуска и объясни их. Проверь доступные сборки и манифесты, явно отметь непроверенный runtime. Открой draft PR. Я должен самостоятельно объяснить Pod/Deployment/Service/PVC, восстановить Pod и проверить сохранность данных.

Оценивать прогресс по способности предсказать результат эксперимента, объяснить наблюдение и написать проверку.
